## Product Requirements Document

**Product / Feature:** Walmart Cart Integration for the Grocery List
**Version:** 1.0
**Author:** Product Owner (delivery pipeline)
**Status:** Draft
**Last Updated:** 2026-08-29

---

### 1. Problem Statement

MealPlanSite's grocery list already computes real purchasable quantities for a curated set of ingredients (`PURCHASE_UNITS` in `src/data/purchaseUnits.ts`, 23 entries) and offers a "Copy list as text" fallback. That copy-paste step was always a stopgap: the user still has to manually re-type or re-search every ingredient on Walmart's site to actually buy it. There is no one-click path from "my grocery list" to "items in a Walmart cart."

MealPlanSite is a static, browser-only React/Vite app hosted on GitHub Pages with no backend and no capacity to hold server-side secrets. This rules out Walmart's two credentialed API surfaces outright (see FR-05), leaving exactly one mechanism capable of adding items to a shopper's cart without a backend: Walmart's affiliate add-to-cart deep link. This PRD scopes the minimum feature that uses that mechanism honestly — one-click add-to-cart for curated items, with a fallback that guarantees no item is ever a dead end, curated or not.

Now is the right time because the purchase-quantity computation and `PURCHASE_UNITS` data model already exist from the prior phase; this phase is additive to that data model, not a rework.

### 3. Success Metrics

Source: Data Analyst metrics definition (`.delivery/artifacts/02-refine/data-analyst/metrics.md`). Consistent with Section 2's constraint statement, no client-side analytics or backend exists for this feature, so every metric below is a build-time, source-derived, or manual-verification check — not a telemetry-collected KPI.

**North Star Metric: Curated Coverage Rate**
- Definition: share of a rendered grocery list's line items that carry a `walmartItemId` and therefore qualify for one-click add-to-cart, versus falling back to search-only.
- Formula: `curated_items_with_walmartItemId / total_grocery_list_items`, surfaced by the "N of M items" UI text (FR-04).
- Target: no fixed numeric target at launch; track directionally so coverage does not regress release-over-release as `PURCHASE_UNITS` grows.
- Observability: manual/build-time count of `walmartItemId`-populated entries in `src/data/purchaseUnits.ts` versus total entries — no runtime instrumentation needed.

### 4. User Personas

**Primary:** Meal planner shopping online — a MealPlanSite user who has selected meals for the week, reviewed the computed grocery list, and wants to buy the resulting ingredients at Walmart without retyping them into Walmart's site or app.

**Secondary:** none named in the idea brief. (Open question OQ-3 below asks whether a "curator" persona — the person hand-maintaining `walmartItemId` values — should be treated as a distinct internal persona for tooling purposes; out of scope for this release either way.)

### 6. Functional Requirements

| ID | Requirement | Priority | Acceptance Criteria |
|----|-------------|----------|---------------------|
| FR-01 | Extend `PurchaseUnitEntry` (`src/data/purchaseUnits.ts`) with an optional `walmartItemId: string` field, keyed the same way as today (lowercased/trimmed `shoppingName ?? name`). Seed the field for as many of the existing 23 entries as can be hand-verified against Walmart product pages, prioritizing high-frequency staples (chicken breast, eggs, olive oil, garlic, onion, brown rice, canned tuna, greek yogurt). **Minimum bar for launch:** all 8 named priority staples above must be curated with a verified `walmartItemId` — "as many as can be hand-verified" is a ceiling on effort beyond the 8 (encouraging more), not a floor below it. A build with fewer than 8 curated staples does not satisfy FR-01. | Must Have | Given the updated `PurchaseUnitEntry` interface, when an entry has no `walmartItemId`, then the entry remains valid and the grocery list still shows a purchase quantity for it (unaffected by this change). Given the 8 named priority staples (chicken breast, eggs, olive oil, garlic, onion, brown rice, canned tuna, greek yogurt), when each of their entries is inspected, then every one of the 8 has a non-empty, all-digit `walmartItemId` sourced from a real `walmart.com/ip/.../<ID>` URL — not just one of the 8. Any additional entries beyond the 8 that are also curated must meet the same verification standard. |
| FR-02 | New pure function `buildCartUrl(items: GroceryItem[]): string \| undefined` in `src/lib/walmartLinks.ts`. For each grocery item, look up `PURCHASE_UNITS[key]?.walmartItemId`; skip items without one. Quantity is the computed purchase quantity (`item.purchase?.quantity`), falling back to `Math.ceil(item.quantity)`, floored at 1. Output format `https://affil.walmart.com/cart/addToCart?items=ID\|QTY,ID2\|QTY2` (URL-encoded via `URLSearchParams`). Returns `undefined` when zero items qualify. **Quantity validity gate:** a computed quantity is valid only if it resolves to a finite number greater than 0 after the fallback chain (`item.purchase?.quantity`, else `Math.ceil(item.quantity)`); an item whose resolved quantity is `0`, negative, `NaN`, `null`, or `undefined` is treated as *not qualifying* for the cart link and is skipped entirely (same as an item with no `walmartItemId`) — it is never floored to 1. Flooring to 1 applies only to a valid, positive quantity that is fractional (e.g., `0.4` -> `1`), never to a zero/negative/missing one.<br><br>**Verified via spike (2026-08-29):** live browser test against the real endpoint confirmed the single-item add, the `ID\|QTY` quantity syntax (cumulative, not a fixed set), and the multi-item comma-joined format all work exactly as specified. Critically, a mixed valid+invalid-ID request added the valid item and silently dropped the invalid one, landing on the cart page (not an error page) — direct confirmation of the graceful-degradation behavior this requirement and NFR-05 depend on for stale/invalid curated IDs. See `spike-findings.md`. **Unresolved caveat:** no publisher/affiliate identifier appeared in the working request despite Walmart's stated Impact-Radius-only restriction — the mechanism is confirmed to *function* technically; whether using it before affiliate enrollment is ToS-compliant is a policy question the spike could not resolve (see OQ-5). Also unconfirmed: Walmart's docs reference a "Consolidated Add to Cart" replacement API with no published timeline or endpoint details — today's endpoint works today, but its longevity is unknown (see Dependencies & Risks). | Must Have | Given a list where every item has a `walmartItemId`, when `buildCartUrl` runs, then it returns a URL containing exactly one `ID\|QTY` pair per item, comma-joined, correctly encoded. Given a mixed list, when `buildCartUrl` runs, then only curated items appear in the output; uncurated items are silently omitted (not errored). Given a list with zero curated items, when `buildCartUrl` runs, then it returns `undefined`. Given an item whose purchase quantity is positive but fractional or below 1 (e.g., `0.4`), when `buildCartUrl` runs, then the emitted quantity is rounded up to 1 and never below 1. Given an item whose resolved quantity is `0`, negative, `NaN`, `null`, or `undefined`, when `buildCartUrl` runs, then that item is skipped and omitted from the output entirely — it does not appear as `ID\|1` or any other value, and this skip does not throw or halt processing of the remaining items. Given a list where every item resolves to an invalid (zero/negative/null/undefined) quantity, when `buildCartUrl` runs, then it returns `undefined`, identical to a list with zero curated items. |
| FR-03 | New pure function `buildSearchUrl(itemName: string): string` in `src/lib/walmartLinks.ts`, returning `https://www.walmart.com/search?q=<encoded name>`. Requires no curated data — works for every item unconditionally.<br><br>**Verified via spike (2026-08-29):** the live spike confirmed the underlying cart mechanism this fallback complements is real and functions as documented (see FR-02); `buildSearchUrl` itself uses Walmart's standard public search path and carries no cart-mechanism risk. | Must Have | Given any item name including spaces or special characters, when `buildSearchUrl` runs, then it returns a syntactically valid, correctly percent-encoded Walmart search URL that a browser can navigate to directly. |
| FR-04 | "Add all to Walmart cart" button in the `GroceryListView.tsx` panel header (beside existing "Copy link"/"Copy list" buttons, reusing `.copy-link-button` styling). Rendered only when `buildCartUrl(...)` returns a defined URL; opens that URL in a new tab (`target="_blank" rel="noopener noreferrer"`). Displays a muted coverage count, e.g. "8 of 14 items." **Empty-list case (M=0):** when the grocery list itself has zero items (nothing selected/computed, before any curation question applies), `buildCartUrl` receives an empty array and returns `undefined` per FR-02; the button, its "N of M items" coverage text, and any per-item search link (FR-06) all render nothing for this state — the same "button absent" treatment as the zero-curated-item case, not a distinct 0-of-0 display.<br><br>**Verified via spike (2026-08-29):** confirms the button's click-through action (single add, quantity, multi-item, graceful degradation on invalid IDs) resolves to real, working cart behavior — see FR-02. | Must Have | Given a grocery list with at least one curated item, when the panel renders, then the button is visible and its label/adjacent text shows an accurate "N of M items" count matching the list's actual curated-vs-total ratio. Given a grocery list with zero curated items (but M>0 total items), when the panel renders, then the button is not rendered at all (not shown disabled), though per-item search links (FR-06) still render for each of the M lines. Given a grocery list with zero items total (M=0, the list is empty), when the panel renders, then the "Add all to Walmart cart" button is not rendered, no "N of M items" coverage text is rendered (not even "0 of 0 items"), and there are no grocery-list lines to carry per-item search links (FR-06 has nothing to attach to). Given the button is clicked, when the new tab opens, then it navigates to the exact URL returned by `buildCartUrl` with no additional processing. |
| FR-05 | Do not attempt to use Walmart's Marketplace/Supplier API (OAuth2 client-credentials) or I/O Affiliate API (RSA-signed) for any part of this feature — both require a server-held secret (impossible on static GitHub Pages) and neither is capable of adding items to a shopper's cart regardless of secret-handling. | Must Have (constraint, not a build item) | Given the shipped code, when reviewed, then it contains zero references to Marketplace/Supplier OAuth flows or I/O Affiliate RSA-signing, and zero API credentials/secrets of any kind in source or bundle. |

### 8. Out of Scope

- Package-size drift as a staleness class distinct from delisting: a curated `walmartItemId` can remain a valid, live product page while its underlying pack size silently changes (e.g., "1 dozen eggs" ID later becomes an 18-count listing), causing quantity math to drift even though the ID itself still "works." Accepted as out of automated-detection scope this release, same as OQ-4's staleness-cadence question — not a new requirement, no AC added.
- Any Walmart product-search, pricing, or stock-availability integration — this requires Walmart's RSA-signed I/O Affiliate API, which is impossible to call securely from a static, backend-less site.
- Instacart or any other retailer integration. Instacart's Developer Platform (`products_link` API) was evaluated and rejected: it requires a developer-owned Bearer secret with no safe home on a static site, plus a ~30–40 day production approval process with no hobbyist path.
- Automated Walmart item-ID discovery, validation, bulk import, or periodic refresh. Curation is manual and will go stale over time (relisted/discontinued products); this is mitigated only by the always-present per-item search fallback (FR-06), never by automation, in this release.
- Bulk sourcing of Walmart item IDs via Walmart's Data Feed API (bestsellers/rollback/category feeds) or Product Lookup API. Both require the *same* Impact Radius affiliate approval as the add-to-cart link itself, so they are not a way around the approval gate — they are a plausible post-approval upgrade path for a later release, not something this release can use to avoid manual curation.
- Any third-party scraped Walmart item-ID dataset (e.g., CrawlFeeds). Evaluated and explicitly excluded as a data source: the known public dataset is small, stale (last updated December 2021), and unofficial/unlicensed — unsuitable as a data source for a shipped feature at any point, not just this release.
- Store selection, price display, delivery/pickup choice, or checkout completion within MealPlanSite itself. The deep link hands the user off to Walmart entirely; MealPlanSite has no visibility into or control over what happens after the new tab opens.
- Any server-side detection or enforcement of Impact Radius affiliate-approval status. The client cannot verify this; see FR-08 and OQ-1.
- Analytics/telemetry on cart-button usage, click-through, or conversion. No backend exists to collect it, and none is added for this feature.
