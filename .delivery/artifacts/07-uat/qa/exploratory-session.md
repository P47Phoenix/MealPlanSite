## Exploratory Testing Session

**Charter**: Explore cross-story interactions between the Walmart Cart Integration stories (1: curated data, 2: buildCartUrl, 3: buildSearchUrl/normalizer, 4: tests, 5: UI wiring, 6: CSS) and pre-existing features (display-mode/show-source-recipes preferences, shareState.ts share links) to discover whether independently-completed stories actually work together, not just in isolation.

**Tester**: QA Engineer (static code-reasoning session — no live browser available in this environment; findings below are marked accordingly)

**Duration**: Standard session (~45 min)

**Date**: 2026-08-29

**Method**: Traced actual code paths across `src/App.tsx`, `src/components/GroceryListView.tsx`, `src/lib/walmartLinks.ts`, `src/lib/groceryList.ts`, `src/lib/preferences.ts`, `src/lib/shareState.ts`, `src/data/purchaseUnits.ts`, and existing test suites (`App.test.tsx`, `GroceryListView.test.tsx`). This is code-reasoning-based, not live interaction — live browser confirmation is still required per the existing MUAT plan.

### Observations

1. Select/deselect recompute chain — `App.tsx` `toggleSelect` mutates `selectedIds` (Set) → `selectedCards` useMemo (keyed on `selectedIds`) → `GroceryListView` receives new `selectedCards` prop → `groceryList` useMemo (keyed on `selectedCards`) → `{cartUrl, curatedCount, totalCount}` useMemo (keyed on `groceryList`). All three cart-related values are computed from a single memo, so `cartUrl` and `curatedCount`/`totalCount` can never go out of sync with each other on a selection change — this is a sound design (confirmed structurally; `GroceryListView.test.tsx` TC-GLV-008 already exercises the `selectedCards`-changes-recompute path at the component level, but no `App.tsx`-level test drives an actual click-select → cart-button-updates path).
2. `App.test.tsx` contains **zero** references to `walmart`, `cartUrl`, `GroceryListView`, or the cart button — the only place selection-to-cart wiring is exercised end-to-end is by passing `selectedCards` directly as a prop in `GroceryListView.test.tsx`. The literal user action of clicking a card tile to select/deselect it and watching the Walmart cart button/count update live is untested by automation and not verified by this session (no browser). This is exactly the seam this charter targets and it is currently a coverage gap, not a confirmed bug.
3. Preferences interaction (`displayMode`, `showSourceRecipes`) — both are independent `useState` hydrated once from `localStorage` via `preferences.ts`, and both only affect line-item *text formatting* (`formatItemLine`, the `(recipe total: …)` note, and the nested source-recipe `<ul>`). Neither is a dependency of the `cartUrl`/`curatedCount`/`totalCount` useMemo, and neither touches `buildSearchUrl`. Traced through the JSX: the per-item `Search` link (`grocery-item__search-link`) is rendered exactly once per `<li>`, unconditionally, before the `showSourceRecipes` conditional block — toggling `showSourceRecipes` on/off, in any combination with `displayMode`, cannot duplicate or remove the search link; it only adds/removes the nested source-recipe list below it. `GroceryListView.test.tsx` TC-SL-005 already covers "showSourceRecipes does not duplicate the search link" at the component level, but does not cross it with `displayMode='purchase+raw'` simultaneously — a plausible but low-risk untested combination.
4. Share-link interaction — `shareState.ts` encodes `selectedIds`, `groceryOpen`, `query`, `mealType`, `activeTags`, `view`/`activeCardId` into the URL; `App.tsx`'s `useEffect` keeps `window.location` in sync via `history.replaceState` on every relevant state change (including `selectedIds`). `GroceryListView.copyLink()` reads `window.location.href` synchronously at click time. Because React state updates and the sync effect run before a user's subsequent click, a copied link reproduces the same `selectedIds` → same `selectedCards` → same `cartUrl`/coverage count when opened fresh. Traced no divergence here. Note: `displayMode` and `showSourceRecipes` are deliberately **not** part of the shareable URL (they're per-browser localStorage prefs, per the doc comment in `preferences.ts`) — so a shared link will reproduce the same Walmart cart/search links and grocery items, but the recipient may see them formatted differently (e.g. without recipe-total annotations) if their local prefs differ. This looks like an intentional consistency choice (cart/search correctness is what's shared; display formatting is per-viewer), not a defect — flagging as a HICCUPPS-Image observation only.
5. Zero-selection / zero-coverage state — with `selectedCards = []`, `groceryList` is all-empty, `getQualifyingItems([])` returns `[]`, `buildCartUrl` returns `undefined`, so the cart button block (`{cartUrl && (...)}`) doesn't render, matching MUAT-04's expectation. Confirmed structurally.
6. Quantity-basis bug (see BUG-01 below): `walmartLinks.ts`'s `resolveQuantity()` falls back to `Math.ceil(item.quantity)` (the raw, *unconverted* recipe-unit quantity) whenever `item.purchase` is `undefined` — but `item.purchase` can be `undefined` for two structurally different reasons that the code doesn't distinguish: (a) the ingredient has no `PURCHASE_UNITS` entry at all (in which case `walmartItemId` is also absent, so the item correctly never qualifies for the cart), or (b) the ingredient **does** have a `PURCHASE_UNITS` entry with a `walmartItemId`, but `computePurchaseQuantity()` in `groceryList.ts` returned `undefined` because the recipe's unit doesn't match the package unit and isn't in the tsp/tbsp/cup volume family (e.g. a mass unit vs. a count unit). In case (b), the item still qualifies for the cart (since `walmartItemId` is present) but the cart quantity added is the raw recipe-unit number, not a package-count — e.g. "3" could mean "3 tsp" while the Walmart item is sold "per head." Checked against the actual curated data in `purchaseUnits.ts` cross-referenced with real ingredient units in `src/data/cards/*.ts`: for the current 8 staples (garlic/clove, onion/each, chicken breast/g, canned tuna/g, eggs/each, olive oil/tbsp, brown rice/cup, greek yogurt/g) every card usage found matches the package unit exactly, so this path is **not currently triggered by live data** — but it is a latent cross-story gap between Story 1 (curated data) and Story 2 (`buildCartUrl`) that would silently add the wrong quantity to a customer's real Walmart cart the moment a future card introduces a garlic/onion/etc. ingredient in a mismatched unit (e.g. "3 tsp minced garlic" instead of "3 clove garlic").

### Bugs Found

- **BUG-01**: `resolveQuantity()` in `src/lib/walmartLinks.ts` uses the raw, unit-unconverted recipe quantity as the Walmart cart quantity whenever `computePurchaseQuantity()` fails to convert units (mass/count mismatch, non-volume-family unit mismatch) but a `walmartItemId` is still present -- Severity: MEDIUM
  - Steps (code path, not live-reproduced): add a card whose ingredient list contains a curated staple (e.g. `garlic`) using a unit that isn't `clove` and isn't in the tsp/tbsp/cup volume family (e.g. `{ name: 'Garlic', quantity: 3, unit: 'tsp', section: 'produce' }`) → `computePurchaseQuantity` returns `undefined` (unit mismatch) → item's `purchase` field is `undefined` → in `getQualifyingItems`, `resolveQuantity` falls back to `Math.ceil(item.quantity)` = `3` → `buildCartUrl` adds `44391372|3` (3 units of the Walmart garlic SKU, which is sold "per head") to the real Walmart cart.
  - Expected: When package-unit conversion fails for a curated item, the item should either (a) still convert correctly, or (b) be excluded from the cart (same as an uncurated item), falling back to the Search link only -- not silently add an unconverted, wrong-basis quantity to a live cart.
  - Actual: The item still qualifies for `buildCartUrl` (since `walmartItemId` lookup and quantity-resolution are decoupled from the conversion-success check), and the quantity added is the raw recipe-unit number rather than a package count.
  - Confirmed by: code reasoning only (`src/lib/walmartLinks.ts` lines 28-32 vs. `src/lib/groceryList.ts` `computePurchaseQuantity`, lines 47-71). Does **not** currently reproduce with any ingredient/unit combination present in `src/data/cards/*.ts` as of this session -- would need either a live browser + a deliberately crafted test card, or a new unit test asserting `getQualifyingItems` excludes items where `purchase` is `undefined` due to conversion failure (as opposed to items with no curated entry at all), to confirm/regress.

### Questions

- Is it intentional that `displayMode`/`showSourceRecipes` are per-browser (localStorage) rather than part of the shareable URL state in `shareState.ts`? (Observation #4 -- looks intentional/reasonable, confirm with PO if a shared link is expected to reproduce the exact same *view*, not just the same *data*.)
- Should `getQualifyingItems` treat "curated but unit-conversion failed" the same as "uncurated" (exclude from cart, Search-link-only fallback)? This seems like the safer default given NFR-07/FR-06's framing of the Search link as the correctness fallback.
